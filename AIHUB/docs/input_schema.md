# 입력 필드 정의 (Input Schema)

결함률 예측 엔드포인트에 전달되는 입력 필드 12개에 대한 설명입니다.
**유효값 제약**은 확정된 사양이고, **관측 범위**는 골든 셋과 실제 데이터에서 관측된 값으로 참고용입니다. 현재 골든 셋은 `data/golden_set_v3.json`(= `golden_set_v3.csv`)이며 단일 턴 60건(C01~C19, P01~P12, N01~N05, A01~A12, I01~I12), 멀티턴 14건(MT01~MT14, `golden_set_v3_multi_turn.csv`)입니다. <!-- [수정] 2026-10-26: v2 -> v3 경로·건수 반영(건수는 CSV의 ID를 직접 세어 확인). v1은 data/v1/, v2는 data/v2/에 보관 --> 필드 설명은 필드명과 데이터에서 정리한 내용입니다.

## 필드 목록

|---|---|---|---|---|---|---|---|

| 2 | `shift` | string | - | 근무조(주간/야간) | `DAY`, `NIGHT` | - | 질의의 "주간조", "밤 근무", "day shift" 등은 코드로 변환 |
| 3 | `supplier_code` | string | - | 입고 자재 공급사 코드 | `SIM-SUP-A`, `SIM-SUP-B`, `SIM-SUP-C` | - | A 비중이 가장 높음 |
| 4 | `planned_quantity` | int | 개 | lot 계획 생산 수량 | - | 약 440 ~ 561 | |

| 6 | `incoming_material_quality_score` | float | 점 | 수입검사 원자재 품질 점수 | - | 약 62 ~ 99 | 값이 높을수록 양호 |

| 11 | `tool_wear_pct` | float | % | 공구 마모율 | **0 ~ 100** (0, 100 유효) | 약 2 ~ 84 | 범위 밖 값은 오류 케이스 (I01: 140, I02: -5) |
| 12 | `days_since_maintenance` | int | 일 | 마지막 설비 정비 후 경과일 | - | 약 1 ~ 60 | 주 단위는 ×7 환산 (2주 → 14). 시간·개월 단위는 모호한 값 |

### 유효값 제약 요약

- `production_line`: `LINE-BPR-01`, `LINE-BPR-02` 외의 값은 존재하지 않음
- `shift`: `DAY`, `NIGHT`
- `supplier_code`: `SIM-SUP-A`, `SIM-SUP-B`, `SIM-SUP-C`
- `fixture_alignment_offset_mm`: 0 이상 (음수 입력은 유효하지 않음)
- `tool_wear_pct`: 0~100 (초과·미만 값은 오류 케이스)

### 현재 코드의 추가 검사 (사양 아님)

<!-- [추가] 2026-10-22: 사양에는 없지만 schema.py DefectRateInput이 차단하는 범위를 명시 -->

위 표에서 유효값 제약이 `-`인 필드도 현재 코드(`aihub/schema.py`의 `DefectRateInput`)는 아래 범위를 검사하고, 벗어나면 `invalid_input`으로 차단합니다. 확정된 사양이 아니며, 유지 여부는 [`architecture.md`](./architecture.md)의 미결 사항에서 관리합니다.

- `planned_quantity`, `days_since_maintenance`: 0 이상 정수 (추출 단계에서 정수로 반올림)
- `ambient_humidity_pct`, `incoming_material_quality_score`: 0~100
- `coating_target_thickness_um`: 0 이상
- `weld_energy_setting_pct`: 0~150
- `process_setting_deviation_pct`: 범위 검사 없음 (음수 허용)

## 공통 규칙

- **값이 없는 경우**: 질의에서 값을 알 수 없으면 해당 필드를 `null`로 두고 `missing_fields`에 필드명을 넣으며, `status`는 `need_more_info`가 됩니다. 누락된 값을 `0` 등으로 채우지 않습니다 (P02).
- **`missing_fields` 구성** <!-- [추가] 2026-10-22: N05(범위 밖 질의) 기대값과 규칙을 일치시키기 위해 명시 -->
  - 기본: 모든 레코드의 `null` 필드 합집합(중복 없음)
  - `invalid_input`: `[]`
  - 예측 요청이 아닌 질의(`records = []`): 추출된 입력이 하나도 없으므로 **12개 필드 전체** (N05)
- **예측 의도 판단과 `records`** <!-- [추가] 2026-10-22: 골든 셋에서 암묵적으로 쓰이던 판단 기준을 명시 -->
  - 예측 의도가 있으면 레코드 1개 이상을 만들고, 값이 전혀 없으면 12개 필드가 모두 `null`인 레코드 1개를 둡니다 (N01~N03).
  - "결함률 예측" 같은 문구 없이 공정 조건만 나열해도 예측 의도로 봅니다 (A01~A05, A07, P08).
  - 예측에 필요한 입력을 묻는 질문도 예측 의도로 보고 전 필드 `null` 레코드를 둡니다 (N04).
  - 공정·예측과 무관한 질의만 `records = []`입니다 (N05).
- **모호한 값**: 값이 있어도 하나로 확정할 수 없으면 `null`로 두고 `ambiguous_fields`에도 필드명을 넣습니다. `status`는 `need_more_info`이며, `ambiguous_fields`는 `missing_fields`의 부분집합입니다 (A01~A07).

  | 유형 | 예시 |
  |---|---|
  | 정성·상대 표현 | "평소보다 높다", "꽤 닳았다", "얼마 전에 정비" |
  | 범위 표현 | "습도 50에서 60% 사이", "460~470개" |
  | 단위 없는 값 | 코팅 두께 "0.08" (mm인지 µm인지 불명) |
  | 미확정 코드 | "BPR 라인 중 한 곳", "저녁 근무", "오후조", "공급사는 A나 B" |
  | 질의 내 번복 | "44.2%라고 했는데 54.2%였나" |
  | 필드를 지목한 기준 참조 | "습도는 평소와 같아요" (기준값을 알 수 없으므로 해당 필드 `null` + `ambiguous_fields`) |

  <!-- [수정] 2026-10-22: 골든 셋 A06·A07에 쓰인 "오후조", "평소랑 비슷한 조건"을 예시에 추가 -->
  <!-- [수정] 2026-10-26 (문서 정정, 로직 변경 없음): "평소랑 비슷한 조건"은 llm.py 프롬프트상 필드를 지목하지 않은 참조(B)라 이 표에서 분리했다. 아래 설명 참고 -->

  - **필드를 지목하지 않은 기준 참조**("평소랑 비슷한 조건")는 어느 필드의 값인지 특정할 수 없으므로 `ambiguous_fields`에 넣지 않고, 전 필드 `null` + `notes`("기준 조건을 알 수 없어 반영하지 않았습니다.")로 처리하도록 프롬프트가 지시합니다(`aihub/llm.py` `[불확실한 값]`의 B). 골든 A06("평소랑 비슷한 조건인데 공구 마모가 좀 심하고 습도도 높아요")의 `ambiguous_fields`가 습도·공구 마모뿐인 것도 같은 기준입니다. 이 구분은 프롬프트 지침이므로 실제 LLM 준수 여부는 별도 평가가 필요합니다.
  - **이미 확인된 필드를 모호하게 바꾸려는 발화** <!-- [추가] 2026-10-26 (로직 변경): pipeline.py run()의 ambiguous_fields 슬롯 비움 처리 반영 -->: 세션에 값이 확인된 필드를 "습도가 꽤 높아졌다면?"처럼 모호하게 바꾸려 하면, 기존 값(예: 54.49)으로 예측하지 않고 증감량도 추정하지 않습니다. 추출 단계에서 해당 필드는 `null` + `ambiguous_fields`가 되고, 파이프라인이 그 필드의 세션 슬롯을 비운 뒤 `missing_fields`·`ambiguous_fields`에 담아 되묻습니다(다른 확인값은 유지, ML 미호출). 이후 수치를 입력하면 그 필드만 새 값으로 바뀌어 예측됩니다. 이 동작은 `test/test_golden_v2.py`의 회귀 테스트(대역 추출)로 다루며, 골든 셋(v3)에 해당 케이스는 없고 실제 LLM이 프롬프트대로 `ambiguous_fields`를 내는지는 확인하지 않았습니다.

- **유효값 검증**: 값을 추출한 뒤 범위·허용값 검증에서 걸러지면 `status`는 `invalid_input`이 되고 `missing_fields`는 비웁니다 (I01~I12). `invalid_input` 응답에는 `ambiguous_fields`가 담기지 않으며(`pipeline._invalid_result`가 설정하지 않음), 같은 발화의 모호한 값은 `null`로 남습니다 (I09). <!-- [수정] 2026-10-26: 골든 v3의 I06~I12 반영, 코드 확인 --> 허용값에 없는 코드(`LINE-BPR-03`, `SIM-SUP-D`)는 비슷한 값으로 치환하지 않습니다.
  - **슬롯이 덜 찬 상태에서도 필드 단위로 검증합니다.** <!-- [추가] 2026-10-23: 이전에는 12개가 모두 찬 뒤에만 검증해 SIM-SUP-D 같은 값이 세션에 저장됐음 --> 값이 있는 필드는 추출 직후(세션 병합 전) `validate_provided_fields()`(`aihub/schema.py`)로 검사하고, 위반하면 `invalid_input`으로 응답합니다. 위반 필드는 세션에 저장하지 않으며, 같은 발화의 유효한 값(라인, 교대조 등)은 유지합니다. 12개가 모두 찬 뒤의 `DefectRateInput` 검증은 안전망으로 남아 있습니다.
- **경계값**: `fixture_alignment_offset_mm = 0`, `tool_wear_pct = 100`은 유효합니다 (C10). 이 값들은 관측 범위 밖이지만 유효값 제약 안입니다. 반대로 `tool_wear_pct = 100.1`은 상한(`le=100`)을 넘으므로 `invalid_input`입니다 (I12). <!-- [수정] 2026-10-26: 골든 I12(100.1)와 schema.py의 le=100 대응을 명시 -->
- **표기 정규화** <!-- [추가] 2026-10-22: 골든 셋 C03에서 쓰이는데 문서에 없던 규칙을 명시 -->
  - 범주형 코드는 대소문자를 가리지 않고 대문자로 정규화합니다 (`line-bpr-01` → `LINE-BPR-01`, `sim-sup-c` → `SIM-SUP-C`). 정규화 후에도 허용값에 없으면 `invalid_input`입니다.
  - 근무조 표현 변환: "주간조"·"day shift" → `DAY`, "밤 근무"·"야간조"·"night shift" → `NIGHT`. "저녁 근무"·"오후조"는 모호한 값입니다.
  - 한글 단위 인식: "퍼센트" → %, "마이크로미터" → µm, "밀리" → mm (C03).
- **단위 환산** <!-- [수정] 2026-10-23: 코팅 두께만 환산하던 규칙을 모든 필드로 확장 -->: 사용자가 필드의 기준 단위와 다른 단위로 입력해도 LLM이 기준 단위로 환산한 값을 추출합니다. 환산했으면 응답의 `notes` 안내에 원래 표현과 환산값을 남기도록 지시합니다(예: "지그 정렬 오차 0.2cm → 2mm").

  | 필드 | 기준 단위 | 환산 규칙 | 예시 |
  |---|---|---|---|
  | `fixture_alignment_offset_mm` | mm | cm ×10, m ×1000, µm ÷1000 | 0.02cm → 0.2 |
  | `coating_target_thickness_um` | µm | mm ×1000, cm ×10000, m ×1000000 | 0.0984mm → 98.4 (C04) |
  | `days_since_maintenance` | 일 | 주 ×7 | 2주 → 14 |
  | `planned_quantity` | 개 | 천 ×1000, 만 ×10000, 천 단위 쉼표 제거 | 1.2천개 → 1200 |
  | `ambient_humidity_pct`, `weld_energy_setting_pct`, `process_setting_deviation_pct`, `tool_wear_pct` | % | "퍼센트"만 인식 | 35.6퍼센트 → 35.6 (C03) |
  | `incoming_material_quality_score` | 점 | 점수 숫자 그대로 | 94.1점 → 94.1 |

  - 필드와 맞지 않는 단위(예: 습도 5mm)나 위 표로 환산할 수 없는 단위(시간·개월)는 값을 넣지 않고 `null` + `ambiguous_fields`로 처리합니다.
  - 환산은 LLM이 수행하므로 준수 여부는 실제 LLM 평가로 확인해야 합니다. 환산 후 범위·허용값 검증은 시스템이 합니다.
  - 반올림: 환산 결과에 `98.39999…` 같은 부동소수점 오차가 생길 수 있어, 추출 후 모든 실수 필드를 소수점 6자리로 반올림합니다(`aihub/pipeline.py`의 `QueryExtractor._coerce`). <!-- [수정] 2026-10-22: 반올림 구현 반영 (이전: 추정·미결) -->
- **항목 표시가 없는 값** <!-- [추가] 2026-10-23 -->: 필드명 없이 값만 적힌 입력("SIM-SUP-B, 480", "80")은 아래 기준으로 처리합니다. 판단은 LLM 추출 프롬프트(`aihub/llm.py`의 `[항목명 없는 값의 필드 결정]` 절)가 하며, 확인된 값이 있는 대화에서는 추출 요청에 `[아직 필요한 값]` 목록(아직 확인되지 않은 필드)이 함께 전달됩니다.

  | 값 종류 | 처리 |
  |---|---|
  | 형태로 필드가 정해지는 문자 | `LINE-…` → `production_line`, `SIM-SUP-…` → `supplier_code`, DAY/NIGHT/주간/야간 → `shift`. 허용값 밖 코드(`SIM-SUP-D`)도 해당 필드로 보고 값은 그대로 두어 검증 단계에서 `invalid_input`이 됩니다. |
  | 수치 | `[아직 필요한 값]` 중 값의 단위와 호환되는 수치 필드가 **정확히 1개**이면 그 필드에 넣습니다. 예: 남은 필드가 `supplier_code`와 `planned_quantity`뿐일 때 "SIM-SUP-B, 480" → 각각 매칭 |
  | 수치 (후보 2개 이상·0개) | 순서·크기로 추측하지 않고 버립니다. `notes`에 "'80'이(가) 어떤 항목의 값인지 알 수 없어 반영하지 않았습니다."를 남기고 되묻기 문구 앞에 표시합니다. 이때 `ambiguous_fields`에는 넣지 않습니다. |
  | 단위 없는 수치가 코팅 두께의 유일한 후보인 경우 | 단위(mm/µm)를 알 수 없으므로 매칭하지 않고 모호한 값(`null` + `ambiguous_fields`)으로 처리하는 것이 골든 기대값입니다 (MT12: "66" → 되묻기, 이어서 "66마이크로미터요" → 확정). 반대로 단위 없는 "20"이 남은 유일한 후보(`days_since_maintenance`)에 매칭되는 경우는 정상입니다 (MT13). |

  - 단위 호환(의도한 기준, 문서상의 정리이며 프롬프트에 이 문장 그대로 들어 있지는 않습니다): 개 → 수량, % → 습도·용접 에너지·설정 편차·공구 마모, 점 → 품질 점수, 일·주 → 정비 경과일, mm·cm·m·µm → 코팅 두께·지그 오차, 단위 없음 → 남은 모든 수치 필드.
  - 항목 표시 없는 수치가 후보 2개 이상을 두고 경쟁하면 버립니다 (MT11: "35%"는 습도·공구 마모가 모두 남아 있어 버림, P12: "480, 55").
  - `[아직 필요한 값]` 목록이 없는 첫 발화는 12개 필드 전체를 목록으로 봅니다 (P10: "80"은 후보가 여러 개라 버림).
  - 단위가 필드를 하나로 특정하는 수치는 항목명이 없어도 그 필드의 값입니다 (예: "480개" → `planned_quantity`, MT10).
  - 이 규칙은 프롬프트로 구현되어 있어 LLM 준수 여부를 실제 호출로 평가해야 합니다.
  - **알려진 프롬프트 한계 (`aihub/llm.py` 재확인, 2026-10-26)** <!-- [수정] 2026-10-26: 이전 서술("규칙 2-1", `(기존 그대로)` 자리표시 문구)은 현재 llm.py에 없어 현재 프롬프트 구조 기준으로 다시 썼다 -->: 현재 프롬프트는 후보를 "`[아직 필요한 값]`의 수치 필드 중 환산표에서 그 단위를 받을 수 있는 필드"로 정의하고 후보가 정확히 1개일 때만 배정하게 합니다. ① **단위 없는 수치의 후보 판정이 명시돼 있지 않습니다.** 위의 "단위 없음 → 남은 모든 수치 필드"는 이 문서의 정리일 뿐 프롬프트 문장이 아니어서, MT13("20" → 정비 경과일)처럼 단위 없는 수치를 남은 유일한 필드에 매칭하는 동작은 LLM의 해석에 맡겨져 있습니다. ② **코팅 두께 예외(MT12)의 우선순위가 명시돼 있지 않습니다.** 프롬프트는 "단위 없는 코팅 두께"를 모호한 값(A)으로 두지만, 그 필드가 남은 유일한 후보일 때 "후보 1개면 배정" 규칙과 어느 쪽이 우선하는지 적은 문장은 없습니다. 두 항목 모두 실제 LLM으로 확인하지 않았습니다. 멀티턴(MT01~MT14)을 실제 LLM으로 실행하는 스크립트는 저장소에 없고, `test/golden_llm_extract.py`는 단일 턴만 실행합니다.
- **비교 질의**: 레코드 여러 개로 분리하고 공통 조건은 각 레코드에 복제합니다. 공통으로 누락된 필드는 모든 레코드에서 `null`입니다 (C07, C08, P06).
- **관측 범위의 의미**: 유효값 제약이 없는 수치 필드(수량, 습도, 품질점수, 코팅 두께, 용접 에너지, 설정 편차, 정비 경과일)의 관측 범위는 참고용이며 검증 기준이 아닙니다. 다만 코드는 관측 범위와 별개로 [현재 코드의 추가 검사](#현재-코드의-추가-검사-사양-아님) 범위를 차단합니다. 이 범위를 사양으로 확정할지는 [`architecture.md`](./architecture.md)의 미결 사항에서 관리합니다.

## 응답 형식

- 엔드포인트 URL은 환경변수 `ai_hub_endpoint_url`로 지정합니다. pydantic-settings는 기본적으로 환경변수 이름의 대소문자를 구분하지 않으므로 `AI_HUB_ENDPOINT_URL`과 같은 설정입니다 (`aihub/config.py`, 출처: https://docs.pydantic.dev/latest/concepts/pydantic_settings/#case-sensitivity).
- 응답은 `data` 키 아래에 있으며, 결함률은 `prediction(defect_rate_pct)` 컬럼(단위 %)으로 반환됩니다. 값은 이미 퍼센트입니다(예: `1.65` = 1.65%, C01 실측 `1.6498678908`).
